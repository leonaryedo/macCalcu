# Mini NPU Simulator

AI의 MAC(Multiply-Accumulate) 연산을 흉내 내는 작은 계산기입니다.  
입력 패턴과 Cross/X 필터를 겹쳐 점수를 내고, 더 높은 쪽을 판정합니다.


MAC(Multiply-Accumulate)연산이란 두 수를 곱하고, 기존 값에 더하기를 하는 연산입니다.
보통 1번 MAC을 하면 한 번 곱하고 한 번 더하게 됩니다. 이를 1FLOPs(부동소수점연산)이라고 한다.

즉, y = x*w + y 형태의 연산이 무수히 많이 벌어지기에 MAC연산이 중요하다.
x = 입력값, w = 가중치, y = 결과

보통 합성곱(Convolution), 행렬 곱셈(Matrix Multiplication)에서 많이 사용된다.

CNN: 필터(가중치)를 입력 특징 맵 위에서 옮겨 다니며 대응 값끼리 곱해 더할 때 합성곱이 일어나고, 그 과정에서 MAC이 반복됩니다.

신경망: 입력 데이터를 여러 층(Layer)을 거치며 변환해 예측 값을 만들어 내고(순전파), 정답과의 차이를 줄이도록 가중치를 조절해 가는(역전파·학습) 일련의 계산 과정입니다.

-기본 단위(MAC, 곱셈-누적, y = x*w + y): 입력(x)과 가중치(w)를 곱해 누적 값(y)에 계속 더합니다.

-층(Layer) 계산(MAC의 묶음): 한 뉴런이나 레이어는 입력들에 가중치를 곱해 더한 뒤(대규모 MAC), 편향(Bias)을 더하고 활성화 함수(ReLU 등)로 꺾어 다음 층으로 넘깁니다. (합성곱이나 행렬 곱셈도 결국 이 MAC을 구조화해 대량 반복하는 것입니다.)

-전체 신경망(MAC의 연쇄): 이런 층들을 여러 개 쌓아 입력이 들어가면 MAC을 수백만~수십억 번 거듭하며 최종 예측을 내놓는 구조가 바로 신경망입니다.한 줄로 요약하면, 신경망은 "MAC 연산을 층층이 쌓아 올린 거대한 계산 파이프라인"입니다.

## 실행 방법

Python 3.8 이상, 표준 라이브러리만 사용합니다. (NumPy 등 외부 패키지 불필요)

```bash
python main.py
```

실행 후 모드를 선택합니다.

1. **사용자 입력 (3×3)** — 필터 A, 필터 B, 패턴을 각 3줄(공백 구분 숫자)로 입력
2. **data.json 분석** — 같은 폴더의 `data.json`을 읽어 일괄 판정·성능 측정·요약 출력

`data.json`은 `main.py`와 같은 디렉터리에 두어야 합니다.

## 구현 요약

### MAC 연산

패턴과 필터의 같은 위치 값을 곱한 뒤 전부 더합니다. NumPy 없이 이중 반복문으로 구현했습니다.

```text
score = Σ (pattern[i][j] × filter[i][j])
```

### 라벨 정규화

`data.json`의 표기가 제각각이라(`+`, `x`, `cross`) 내부에서는 표준 라벨만 씁니다.

| 입력 | 표준 라벨 |
|------|-----------|
| `+`, `cross` | Cross |
| `x` | X |

PASS/FAIL 비교와 콘솔 출력도 이 표준 라벨 기준입니다.

### 판정·동점 정책

- Cross 점수 > X 점수 → `Cross`
- X 점수 > Cross 점수 → `X`
- `|Cross − X| < 1e-9` → `UNDECIDED` (부동소수점 동점)

모드 1에서는 필터를 A/B로 부르므로 판정은 `A` / `B` / `판정 불가`로 출력합니다.

### 부동소수점 오차 -> 허용오차(episilon)기반 비교

**부동소수점(floating-point)**은 컴퓨터가 소수를 저장하고 계산하는 방식입니다. 

숫자를 다음처럼 유효숫자와 지수로 나누어 표현합니다.

1230 = 1.23 × 10³

0.00123 = 1.23 × 10⁻³

소수점의 위치가 지수에 따라 “떠다니듯” 바뀌기 때문에 floating point라고 부릅니다. 

컴퓨터는 보통 이 방식을 2진수로 사용하고, 저장 공간도 유한합니다. 

그런데 0.1처럼 2진수로 정확히 표현되지 않는 숫자가 있어, 가장 가까운 값으로 반올림해 저장합니다.

즉, 십진수 0.1은 분수로 1/10인데, 2진수로 바꾸면 다음처럼 끝없이 반복됩니다.

0.1₁₀ = 0.00011001100110011...₂

컴퓨터는 저장 공간이 한정되어 있으므로 이 반복되는 숫자를 끝까지 저장할 수 없습니다. 

소수를 메모리에 근삿값으로 저장하는 경우가 많습니다. 가장 가까운 값으로 반올림해 저장하죠. 

그래서 계산 결과에 아주 작은 오차가 생길 수 있습니다

예: 0.1 + 0.2가 정확히 0.3이 아니라 0.30000000000000004처럼 나올 수 있습니다.

결과를 ==로 정확히 비교하면 이런 작은 차이도 불일치로 판단합니다. 

계산이 여러 번 누적되는 MAC에서는 미세한 오차가 생길 수 있으므로, 

이 때문에 올바른 결과가 FAIL 처리될 수 있습니다.

그래서 실제 값과 기대값의 차이가 정해 둔 허용 범위 안이면 같은 결과로 보는 허용오차 기반 비교를 사용합니다. 

### 입력·스키마 검증

- 모드 1: 행/열 개수나 숫자 파싱이 틀리면 안내 문구 후 재입력
- 모드 2: 크기 불일치·라벨 오류 등은 해당 케이스만 FAIL 처리하고 프로그램은 계속 진행

## 결과 리포트

### 모드 2 실행 결과

총 테스트 6개 — 통과 3 / 실패 3

| 케이스 | Cross | X | 판정 | expected | 결과 |
|--------|-------|---|------|----------|------|
| size_5_1 | 0.9 | 0.8999999999999999 | UNDECIDED | X | FAIL |
| size_5_2 | 8.9 | 0.1 | Cross | Cross | PASS |
| size_13_1 | 0.3 | 14.700000000000008 | X | X | PASS |
| size_13_2 | 7.499999999999997 | 7.5 | UNDECIDED | Cross | FAIL |
| size_25_1 | 4.9 | 4.899999999999999 | UNDECIDED | X | FAIL |
| size_25_2 | 52.9 | 0.1 | Cross | Cross | PASS |

### 실패 원인 분석

실패 3건(`size_5_1`, `size_13_2`, `size_25_1`)은 MAC 계산 오류나 JSON 스키마 문제가 아닙니다.  
두 필터 점수가 `1e-9` 안으로 거의 같아 **epsilon 동점 규칙**에 따라 `UNDECIDED`가 나왔고, expected는 `Cross`/`X`라서 FAIL로 집계됩니다.

원인은 부동소수점 표현입니다. 예를 들어 `size_5_1`에서 Cross는 `0.9`, X는 `0.8999999999999999`처럼 보여 사람이 보기엔 동점인데, 비트 단위로는 미세한 차이가 납니다.  
허용오차 안이면 “어느 쪽이 더 유사한지 단정할 수 없음”으로 처리하는 것이 이번 비교 정책이므로, 이 FAIL은 오답이라기보다 수치 비교 이슈를 정책대로 드러낸 결과입니다.

반대로 PASS 3건은 라벨 정규화(`+`→Cross, `x`→X)와 MAC 결과가 expected와 일치한 경우입니다.  
정규화를 빼면 문자열 불일치만으로도 FAIL이 대량 발생할 수 있습니다. 스키마·크기 불일치 FAIL은 없었고, 실행 중 비정상 종료도 없었습니다.

### 성능 분석과 시간 복잡도

각 크기마다 MAC만 10회 반복 측정한 평균입니다. (파일 I/O·출력 시간 제외)

| 크기 | 평균 시간(ms) | 연산 횟수 (N²) |
|------|---------------|----------------|
| 3×3 | 0.001 | 9 |
| 5×5 | 0.001 | 25 |
| 13×13 | 0.005 | 169 |
| 25×25 | 0.017 | 625 |

MAC은 칸마다 곱·누적을 한 번씩 하므로 연산량은 **N²**이고 시간 복잡도는 **O(N²)**입니다.  
실측에서도 N이 커질수록 시간이 늘었고, 연산 횟수 9→625(약 69배)에 맞춰 25×25가 3×3보다 느려졌습니다.  
ms 절대값은 환경에 따라 달라질 수 있지만, “크기가 커지면 제곱으로 연산이 늘고 시간도 는다”는 경향은 재현됩니다.
여기에서 o는 빅오(Big O)표기법으로 입력 크기 N이 커질 때 실행 시간이나 메모리 사용량이 어떤 속도로 증가하는지 나타내는 방법이다. 실제 연산 횟수는 예를 들어 3N² + 5N + 2처럼 여러 요소로 구성될 수 있습니다. N이 충분히 커지면 가장 빠르게 커지는 N² 항이 전체 증가를 좌우하므로, 작은 항과 상수는 생략해 O(N²)라고 씁니다.
O(1): 입력 크기와 무관하게 일정
O(N): 입력 크기에 비례
O(N²): 입력 크기의 제곱에 비례
O(N³): 입력 크기의 세제곱에 비례
....

### CPU(직렬) vs NPU(병렬)
현재 Python 구현은 CPU에서 각 칸의 곱셈·누적을 순서대로 수행하므로, 작업량이 커지면 연산이 직렬로 쌓이는 것이 병목이 될 수 있습니다. 
NPU는 여러 MAC 연산을 병렬로 처리해 큰 입력이나 같은 연산을 많이 반복하는 작업에서 유리하지만, 입력·필터를 NPU 메모리로 옮기는 시간과 메모리 대역폭이 충분하지 않으면 연산 장치가 데이터를 기다리게 됩니다. 
특히 3×3처럼 작은 작업은 전송·실행 준비 비용이 병렬 처리로 얻는 이득보다 커 CPU가 더 빠를 수 있으므로, 충분한 병렬 작업량과 데이터 재사용이 있고 데이터 공급 대역폭도 뒷받침되는 지점에서 NPU 전환 효과가 커집니다.

### 큰 입력에서 생길 수 있는 문제와 해결 순서
예를 들어 100×100 패턴에는 숫자 1만 개가 있지만, 1000×1000 패턴에는 100만 개가 있습니다. 크기를 10배 키우면 계산량과 숫자를 담을 공간은 약 100배가 되므로, 패턴이 많으면 처리 시간이 길어지고 메모리도 부족해질 수 있습니다. 현재 프로그램은 `data.json`의 케이스를 한 번에 읽기 때문에 케이스가 많아질수록 메모리 부담이 커집니다.

먼저 파일을 읽는 시간과 MAC 계산 시간을 따로 재어 어느 쪽이 느린지 확인합니다. 파일 읽기가 문제라면 JSONL 스트리밍(JSON Lines Streaming)을 적용할 수 있습니다. JSONL은 케이스마다 한 줄씩 저장하는 형식으로, 모든 케이스를 한꺼번에 보관하지 않고 한 줄씩 읽어 처리합니다. 

패턴 하나가 너무 커 계산이 오래 걸리면, 예를 들어 1000×1000 표를 여러 작은 구역(블록)으로 나누는 블록화(tiling: 큰 행렬을 작은 타일로 나누기  or blocking)를 적용하고, 각 구역의 점수를 계산해 누적하는 부분합 누적(partial-sum accumulation)을 할 수 있습니다. 같은 계산을 여러 숫자에 한꺼번에 적용하는 벡터화(vectorization)를 먼저 검토하고, 그래도 계산이 느릴 때 여러 구역을 동시에 처리하는 병렬화(parallelization)를 고려합니다. 

단, 작업을 지나치게 잘게 나누거나 처리 장치로 데이터를 옮기는 데 시간이 많이 들면 오히려 느려질 수 있으므로, 작은 예제부터 시간을 비교하며 적용해야 합니다.
